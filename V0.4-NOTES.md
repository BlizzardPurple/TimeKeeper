# TimeKeeper v0.4 — Planning Notes

## Issues from v0.3 Testing

### 1. Widget out of sync with app

**Problem:** The widget doesn't reflect the app's current state reliably. The Glance widget state reads from Room/DataStore independently and only refreshes every 15 minutes (Android minimum) or on explicit check-in/out events. If the user checks in from the app, the widget may show stale "OUT" status until the next periodic refresh or manual interaction.

**Root cause analysis:**
- Glance widgets don't support real-time updates — Android batches widget refreshes
- The `TimeKeeperWidgetStateDefinition` reads a snapshot from Room each time, but it only gets called on explicit `widget.update()` or the 15-min periodic refresh
- There's no mechanism to push live elapsed time to the widget between refreshes

**Proposed fix — Stopwatch widget approach:**
- Instead of trying to keep a static snapshot in sync, build the widget as a **live stopwatch** display
- Show a running timer that ticks (use `updatePeriodMillis` at minimum 30 min + manual updates on state changes)
- On check-in: widget shows "▶ 0h 0m" and starts counting
- On check-out: widget shows "⏸ Xh Ym" (today's total, frozen)
- The stopwatch feel makes staleness less noticeable — even if the widget is 1-2 min behind, the running timer gives the right impression
- Still keep the check-in/out toggle button on widget
- **Key insight:** Android Glance doesn't support real-time timers natively. Options:
  - a) Use `Chronometer` RemoteView (requires fallback from Glance to traditional RemoteViews for the timer row)
  - b) Use a foreground service to update the widget every 60 seconds while checked in
  - c) Accept the 15-min refresh and just show "checked in since HH:MM" with a calculated elapsed time at each refresh
- **Recommendation:** Option (c) is simplest and battery-friendly. Show "IN since 9:15 AM" + calculated elapsed at last refresh. The app has the real-time timer — the widget is a glance, not a live clock.

### 2. Checkout notification radius too large (100m)

**Problem:** The 100m exit geofence triggers "Leaving office?" notifications too easily — stepping outside the building for a moment, going to a nearby shop, etc.

**Proposed fixes:**
- a) **Reduce exit radius** — Drop from 100m to something tighter. But the outer ring is also used for arrival notifications, so we'd need to decouple:
  - Arrival notification: keep at 100m (gives early heads-up)
  - Departure notification: use a separate, smaller radius (e.g. 200-300m, counterintuitively larger so you have to actually LEAVE the area)
- b) **Add dwell delay to exit** — Only fire the checkout notification if the user has been OUTSIDE the radius for X minutes (e.g. 5 min). Prevents false alarms from brief steps outside.
- c) **Configurable exit radius** — Let the user set the checkout sensitivity in Settings separately from the arrival radius
- d) **Smart exit** — Don't show checkout notification if total session < 30 min (probably a false alarm)
- **Recommendation:** Option (b) — add a 5-minute delay after exiting the 100m zone before firing the checkout notification. If the user re-enters within 5 min, cancel the pending notification. This handles the "stepped out briefly" case without adding complexity.
